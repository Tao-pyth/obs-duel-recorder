# v0.2 Worker Core API — Acceptance Checklist

This document defines the acceptance criteria for **v0.2 - Worker Core API** as described in:

- `docs/roadmap.md` (canonical roadmap)
- `AGENTS.md` (responsibility separation + runtime rules)
- `docs/requirements/requirements.md` (high-level requirements)

This checklist is intentionally **docs-first** and is meant to be reviewed before implementation.

## Scope

v0.2 focuses on:

- A minimal Python Worker that can start reliably
- A minimal localhost HTTP API (FastAPI)
- A stable `GET /health` endpoint
- Configuration-loading scaffolding (no secrets in git)
- Logging initialization (files under `user_data/logs/`)
- Runtime directory creation (restart-safe)

## Non-goals (explicitly out of scope for v0.2)

- SQLite schema, migrations, or persistence implementation
- Queue processing, upload processing, OCR, template matching
- OBS Plugin lifecycle management or UI
- YouTube OAuth/token handling

## Terms

- **Application files** live under `app/`
- **Runtime data** lives under `user_data/` and must not be committed

## Acceptance Checklist

### A. Startup / Entrypoint

- [ ] A single, documented Worker entrypoint exists (CLI command or `python -m ...`).
- [ ] The Worker can start without requiring OBS.
- [ ] Startup is restart-safe (no destructive deletes of runtime data).
- [ ] Startup clearly logs the effective host/port and runtime paths.

### B. Runtime Directory Creation

- [ ] Startup ensures required directories exist under `user_data/` (create-if-missing, no overwrite):
  - [ ] `user_data/config/`
  - [ ] `user_data/data/`
  - [ ] `user_data/logs/`
- [ ] Directory creation is idempotent.
- [ ] If a directory is not writable, the Worker fails fast with an actionable error.

### C. Logging Initialization

- [ ] Logging initializes early in startup.
- [ ] Logs are written under `user_data/logs/`.
- [ ] Logs are preserved by default (no automatic deletion).
- [ ] Startup logs include (at minimum):
  - [ ] Worker version (or explicit `unknown` placeholder)
  - [ ] host/port
  - [ ] config path (or “no config loaded”)
  - [ ] `user_data/` base dir and `logs_dir`

### D. Configuration Loading (Scaffold)

- [ ] A config-loading module/scaffold exists and is documented.
- [ ] Default behavior is explicit: Worker can start with no user config present.
- [ ] The intended runtime config location is under `user_data/config/`.
- [ ] Secrets/OAuth credentials are **not** stored in git; the following remain ignored:
  - [ ] `config/secrets/`
  - [ ] `user_data/config/secrets/`

### E. FastAPI App + Localhost HTTP API

- [ ] A FastAPI app exists and is served on localhost by default.
- [ ] API surfaces are documented as “v0.2 Worker Core API”.
- [ ] Error responses follow a stable JSON shape suitable for future OBS Plugin UX:
  - [ ] `code: str`
  - [ ] `message: str`
  - [ ] `details?: object`

### F. `GET /health` Endpoint

- [ ] `GET /health` returns HTTP 200 when the Worker is running.
- [ ] Response is JSON and stable across patch releases.
- [ ] Response contains enough signal for future OBS Plugin diagnostics (minimum):
  - [ ] `status` (e.g. `ok` / `degraded`)
  - [ ] `version`
  - [ ] `uptime_seconds`
  - [ ] `config_loaded` (boolean)
  - [ ] `runtime_dirs_ok` (boolean)
- [ ] If startup is partially degraded (e.g. logging fallback), `/health` reflects that with `status=degraded` and details.

### G. Shutdown Behavior

- [ ] Shutdown is documented (what signals are supported, what cleanup is performed).
- [ ] Shutdown does not delete runtime data.

### H. Smoke Tests / Developer Notes

- [ ] A smoke-test or developer note exists describing how to verify:
  - [ ] Worker starts
  - [ ] runtime dirs exist
  - [ ] `/health` returns 200
- [ ] The verification instructions do not require OBS.
