# v0.8 Template Matching MVP - Acceptance Checklist

This document defines the acceptance criteria for **v0.8 - Template Matching MVP** as described in:

- `docs/roadmap.md`
- `docs/requirements/requirements.md`
- #249

## Scope

v0.8 creates the first automatic duel detection boundary:

- template matching engine
- local template loading
- template configuration management
- duel lifecycle state transitions
- duel start detection
- duel end detection
- recording trigger integration through the v0.6 recording lifecycle API

## Non-goals

- Shipping Yu-Gi-Oh! Master Duel assets or user-provided templates.
- OCR-driven primary detection.
- Full image-processing engine replacement.
- YouTube upload execution.
- Screenshot capture and screenshot archive behavior reserved for v0.9.

---

## Acceptance Checklist

### A. Template Matching Engine

- [x] Worker exposes a bounded template matching interface.
- [x] Local templates are loaded from `user_data`, not from repository assets.
- [x] Missing template config produces an explicit empty-template state.
- [x] Missing or empty template files produce diagnostics and are not silently treated as matches.
- [x] Matching behavior is covered by tests with local text/byte fixtures.

### B. Template Configuration Management

- [x] Template configuration format is documented.
- [x] Config load and validation behavior is tested.
- [x] Invalid config failures are diagnosable.
- [x] Runtime/user data boundaries are documented.

### C. Duel Lifecycle State Transitions

- [x] Worker represents `no_duel`, `potential_duel`, `active_duel`, and `ended_duel`.
- [x] Start and end confirmation counts debounce obvious single-frame false triggers.
- [x] Transition behavior is deterministic and covered by tests.
- [x] MVP false-positive/false-negative assumptions are documented.

### D. Recording Trigger Integration

- [x] Confirmed duel start sends recording `start` through the existing recording boundary with source `automatic`.
- [x] Confirmed duel end sends recording `stop` through the existing recording boundary with source `automatic`.
- [x] Recording transition conflicts are returned as detection events instead of crashing detection.
- [x] Integration behavior is tested through Worker API tests.

### E. Worker API Boundary

- [x] Worker exposes detection template, state, and frame evaluation endpoints.
- [x] API payloads are validated with stable error codes.
- [x] Existing `/health`, `/version`, `/overlay/state`, `/recording/*`, and `/queue/*` compatibility is preserved.
- [x] Worker tests cover template config, matching, lifecycle transitions, recording integration, and invalid payloads.
