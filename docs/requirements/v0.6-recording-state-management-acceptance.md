# v0.6 Recording State Management - Acceptance Checklist

This document defines the acceptance criteria for **v0.6 - Recording State Management** as described in:

- `docs/roadmap.md`
- `docs/requirements/requirements.md`
- #247

## Scope

v0.6 creates the first stable recording lifecycle management layer:

- recording state tracking
- manual start and stop controls
- automatic/manual state synchronization boundary
- interrupted recording discard logic
- recording recovery handling
- Worker/Plugin diagnostics for lifecycle decisions

## Non-goals

- Queue Recovery System work reserved for v0.7.
- Automatic Duel Recording and template matching work reserved for v0.8.
- Upload/OAuth work reserved for v1.0+.
- OCR-driven recording triggers.
- Persisting runtime videos, screenshots, logs, databases, or generated media in the repository.

## Terms

- **Recording session**: one lifecycle attempt from start request through final stop, discard, or recovery.
- **Manual command**: an operator-initiated start or stop request from the Plugin/Dock or API.
- **Automatic command**: a future detector-initiated command. v0.6 must define the synchronization boundary without implementing v0.8 detection.
- **Authoritative state**: the Worker-owned state exposed through the localhost API and persisted when durability is required.
- **OBS control**: OBS recording start/stop calls owned by the Plugin.

## Acceptance Checklist

### A. Recording State Model

- [x] A canonical contract defines stable v0.6 recording states.
- [x] Allowed transitions are documented and enforced.
- [x] Invalid transitions return deterministic diagnostics and do not corrupt state.
- [x] State responses expose enough information for Plugin/Dock display and smoke verification.
- [x] The model distinguishes idle, starting, recording, stopping, completed, interrupted, and error/recovery cases.

### B. Manual Start And Stop Controls

- [x] Manual start can request a transition from idle to a start-pending/recording path.
- [x] Manual stop can request a transition from recording to a stop-pending/completed path.
- [x] Repeated start/stop commands are deterministic and diagnosable.
- [x] Plugin/Dock controls surface command success/failure without requiring users to inspect logs first.
- [x] Manual controls do not take ownership of v0.8 automatic detection.

### C. Automatic / Manual Synchronization Boundary

- [x] Automatic and manual commands use the same state transition rules.
- [x] Conflicting commands cannot create duplicate recording sessions.
- [x] Stop commands are idempotent or produce a clear no-op/conflict diagnostic.
- [x] Future v0.8 detection can call the v0.6 boundary without redefining lifecycle state.

### D. Interrupted Recording Discard And Recovery

- [x] Startup or restart can detect interrupted in-progress recording state.
- [x] Interrupted recordings have explicit discard/recovery outcomes.
- [x] Discard/recovery behavior is restart-safe and avoids deleting unrelated user files.
- [x] Runtime data safety boundaries are documented.
- [x] Recovery diagnostics identify the session and resulting state.

### E. Worker / Plugin API Boundary

- [x] Worker exposes the recording state and command boundary through localhost API routes.
- [x] API payloads are validated with stable error codes.
- [x] Existing `/health`, `/version`, and v0.5 `/overlay/state` compatibility is preserved.
- [x] Overlay recording-state display can be driven from the authoritative recording state.
- [x] Worker tests cover state defaults, valid transitions, invalid transitions, and recovery behavior.

### F. OBS Runtime Smoke

- [x] A v0.6 smoke procedure exists.
- [x] Smoke evidence records the tested commit SHA on `main`.
- [x] Smoke evidence proves Plugin load, Worker health, manual start/stop controls, recording-state API, overlay state synchronization, and recovery/discard diagnostics.
- [x] Smoke evidence is redaction-checked before being posted to the tracking issue.
- [x] OBS shutdown or harness cleanup issues are distinguished from Plugin/Worker failures.
